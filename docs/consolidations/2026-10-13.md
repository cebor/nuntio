## Target picture

**nuntio core (app, window, tabs, panes).** `Core` coordinates services and dispatches actions; `WindowState` owns the window, the renderer and the input state and offers lifecycle operations instead of having its fields poked. Pure model types (pane tree, tabs, renderer health, banner identity, repeat-to-confirm) carry their own invariants and tests and have no window or GPU types. One function owns each repeated sequence (font application, window grabs, helper launches).

**nuntio UI and input.** Every overlay is a pure layout-plus-draw module over one `UiMetrics` (pixel snapping) and one `style::Palette` (bar, separator, frame colors derived once from the theme), returning the same `(Vec<UiRect>, Vec<UiText>)` shape. Banners are identified by a topic, not by title text. Key bindings store the config's `KeyCombo`; key encodings (keys, focus reports, wheel arrows, function keys) live in `input.rs`; menu titles come from `Action::label`.

**Services and platform glue.** WSL and Windows path translation has one UNC parser in `wsl.rs`; `running_in_wsl` is the one answer to "inside WSL". Shared contracts that several binaries rely on (the `NUNTIO_CONFIG` name and config path precedence, `~` expansion and display, the atomic writer) live in `nuntio-config`. `nuntio-wsl` stays a tiny relay with a small framed protocol.

**nuntio-term.** A thin `TermHandle` facade over small modules; launch intent is one `Program` enum; each per-pane fact has one owner; lock-poison handling is one helper; OS-specific process inspection sits in one cfg'd `sys` module per OS; the integration tests share one harness.

**nuntio-render.** The renderer turns a `Frame` and `Snapshot`s into pixels. Text size is a `TextSize`, the frame layout is a `Layout` that owns its ranges, one `Mask` type serves box drawing and decorations, errors are `RenderError`. A split of `Renderer` into quad, glyph-cache and image-cache modules is the next step (see greenfield observations).

**nuntio-config and nuntio-config-tui.** `nuntio-config` owns everything about the config file and user paths, plus coupling rules between settings (the update indicators), so the editor applies results instead of encoding rules. The editor keeps its `Store`-trait logic and the single `SETTINGS` schema.

**nuntio-apps and the shared TUI layer.** Both terminal apps sit on `nuntio-tui` (terminal modes, panic restore, key normalization, OSC 52 copy, single-line `TextInput`, tones). `nuntio-apps` stays one binary with one module per app; the notes app has a separate failure screen and a typed save outcome.

**Tooling and packaging.** xtask has one argument parser that rejects leftovers, one `on_path`, one Linux install tree for tarball and AppImage, and render sizes derived from the per-format icon lists. CI fails when a package tool is missing (`NUNTIO_PACKAGE_STRICT`).

**Documentation.** ARCHITECTURE.md owns crates, threads, invariants and "Where to change what"; AGENTS.md owns commands, the gate and the drive workflow; docs/config.md is the settings reference with a test that each setting has a row in its own table.

## Greenfield observations

- `Renderer` (≈1,500 lines): split into `quad` (instances, pipelines, instance buffer), `glyphs` (font, atlases, the clear-or-grow policy) and `images` (image atlas and uploads), each with its own overflow handling.
- One stream scanner in nuntio-term for every intercepted escape (OSC 1337, `CSI 16 t`, OSC 7 and 9;9), instead of two state machines over the same bytes.
- `WindowState` lifecycle operations (`open_tab`, `close_tab`, `remove_pane`) that own the focus transition; then `attention_requested` and the drag state become private.
- `app.rs` (≈1,500 lines): the cfg-per-OS window helpers, clipboard and theme/update services as modules beside `Core`.
- The notes `App` (≈1,500 lines in `state.rs`): split along its sections once a second app shares the crate.
